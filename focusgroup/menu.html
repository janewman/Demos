Menu & Menubar Pattern

Vertical menus and menubars with nested submenus using independent focusgroup scopes.

Simple Vertical Menu

A basic vertical menu with Up/Down arrow navigation.

focusgroup="menu"
Try it: Tab to (or click) a menu item, then use ↓ and ↑ to navigate between items.
  • menu defaults to block wrap (Up/Down with wrapping). This demo uses those defaults.
  • The menu is a single tab stop. Arrow keys navigate within.
  • No JavaScript needed for navigation
View source 
<div focusgroup="menu" aria-label="File actions"
     class="menu-vertical">
    <button type="button" class="menu-item">New</button>
    <button type="button" class="menu-item">Open…</button>
    <button type="button" class="menu-item">Save</button>
    <button type="button" class="menu-item">Exit</button>
</div>

Menubar with Popover Submenus

A horizontal menubar. menubar defaults to inline (Left/Right) navigation between top-level items. Each submenu is a focusgroup="menu" (defaulting to block, Up/Down navigation) that's revealed via the popover attribute. To make this work under the @microsoft/focusgroup-polyfill as well as native, the submenus initialize as focusgroup="none" and a small toggle handler flips them to focusgroup="menu" on open and back on close — see "Polyfill consideration" below.

focusgroup="menubar"
Try it: Tab to the menubar. Use → ← to move between top-level items. Press Enter or Space to open a submenu, then use ↓ ↑ inside. Press Escape to close and return focus to the menu bar item.
  • menubar defaults to inline wrap (Left/Right with wrapping). No explicit modifiers are needed.
  • menu defaults to block wrap (Up/Down with wrapping). No explicit modifiers are needed.
  • Nested focusgroups are independent scopes. They don't interfere with each other.
  • The popover attribute handles submenu visibility
  • The spec leaves the orthogonal axis (Up/Down on the menubar) free for authors. JavaScript can open/close submenus with those keys as a progressive enhancement.
  • This demo initializes submenus with focusgroup="none" and switches them to focusgroup="menu" when the popover opens. The next section explains why.
View source 
<ul role="menubar" focusgroup="menubar"
     aria-label="Application Menu" class="menubar">
    <li role="none">
        <button role="menuitem" type="button" class="menubar-item"
             aria-haspopup="menu" aria-expanded="false"
             popovertarget="filemenu">File</button>
        <!-- The submenu starts with focusgroup="none" while hidden.
             A small `toggle` listener (see the inline script at the
             bottom of this page) switches it to focusgroup="menu" when
             the popover opens, then back to "none" when it closes.
             With that attribute change, arrow-key behavior works in
             both native focusgroup and @microsoft/focusgroup-polyfill;
             the polyfill doesn't observe popover visibility directly. -->
        <ul role="menu" focusgroup="none"
             id="filemenu" popover aria-label="File submenu" class="submenu">
            <li role="none"><button role="menuitem" type="button" class="submenu-item"
                 autofocus>New</button></li>
            <li role="none"><button role="menuitem" type="button" class="submenu-item">Open</button></li>
            <li role="none"><button role="menuitem" type="button" class="submenu-item">Save</button></li>
        </ul>
    </li>
    <!-- More menu items... -->
</ul>

Polyfill Consideration: Popover Submenus

The submenu HTML in the demo above starts each <ul role="menu"> with focusgroup="none" rather than the focusgroup="menu" you'd expect from the spec. A small inline toggle listener on each popover then writes focusgroup="menu" on open and resets to focusgroup="none" on close.

Under native focusgroup, this attribute toggle is a no-op. Arrow-key navigation within a submenu only matters when the submenu is visible, and the native implementation handles either pattern.

Under the @microsoft/focusgroup-polyfill, the toggle is required. The polyfill scans for focusgroup-bearing elements once when it loads and then uses a MutationObserver to watch for added elements and attribute changes — but it does not observe popover visibility changes. A submenu that's already in the DOM as focusgroup="menu" but hidden would have its items excluded by the polyfill's visibility checks during the initial scan, and never re-evaluated when the popover opens. The documented workaround is to start hidden focusgroups as focusgroup="none" and switch to a meaningful behavior token only while they're visible, which is what this demo's toggle handler does.

If you copy this demo's pattern into your own code and need to support browsers without native focusgroup, replicate the toggle handler — or your popover-revealed submenus will be silently un-navigable in polyfilled mode.

View the toggle handler 
document.querySelectorAll("[popovertarget]").forEach(trigger => {
    const popover = document.getElementById(trigger.getAttribute("popovertarget"));
    if (!popover) return;
    popover.addEventListener("toggle", e => {
        const isOpen = e.newState === "open";
        trigger.setAttribute("aria-expanded", String(isOpen));
        if (isOpen) {
            // Guard the rAF against rapid close-before-frame.
            requestAnimationFrame(() => {
                if (popover.matches?.(":popover-open")) {
                    popover.setAttribute("focusgroup", "menu");
                }
            });
        } else {
            popover.setAttribute("focusgroup", "none");
        }
    });
});

Key Point: Independent Nested Scopes

When a focusgroup is nested inside another, they are completely independent. Each has its own navigation axis, wrapping behavior, memory, and entry point. Arrow keys only affect the focusgroup that currently has focus within it.

In the menubar example above:

  • Left/Right arrows navigate the menubar (inline axis)
  • Up/Down arrows navigate within an open submenu (block axis)
  • Tab moves focus out of the submenu and continues through the normal tab order
